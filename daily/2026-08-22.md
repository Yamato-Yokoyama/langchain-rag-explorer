## 学び①: Router は2段階の LLM 判定でできている(Subintent 設計)

Router は1回の LLM 呼び出しで終わりではなく、**2階層**になっている。

### 第1階層: `route()` — トップレベル intent 判定

`semantic` / `aggregation` / `table_display` の3つに分類。ここで `aggregation` と判定されたクエリだけが次の階層に進む。

### 第2階層: `handle_aggregation` 内の sub_intent 判定

`aggregation` と判定された後、**さらに** LLM が「どの集計関数を使うか」を分類する:

| sub_intent | 対応する関数 | 例 |
|---|---|---|
| `sum_by_month` | `sum_by_month(df)` | 「4月の合計は?」 |
| `count_by_month` | `count_by_month(df)` | 「月に何回買った?」 |
| `top_n_by_price` | `top_n_by_price(df, n)` | 「一番高かったのは?」 |
| `total_all` | `total_all(df)` | 「全部でいくら?」 |

`sub_intent` が決まったら `FUNC_MAP` で実関数に dispatch、pandas が決定的に計算 → その生の結果(dict/float/DataFrame)を**また別の LLM 呼び出し**で自然文に整形して返す。

つまり1つの集計クエリに対して、実際には **LLM 呼び出しが2回**(トップレベル intent 判定 + sub_intent 判定)+ 整形で **合計3回** 走っている。集計そのもの(数値計算)は pandas が決定的にやるので Day 10 の arithmetic bottleneck は解消されているが、「どの処理に振り分けるか」の判断自体はまだ LLM に依存している。

## 疑問: Router の判断を LLM に頼っている部分、実務ではどうしてるんだろう

`route()` も sub_intent 判定も Option A(LLM ベース)で実装した。sketch(`docs/router-design-sketch.md`)でも Option B(rule ベース)、Option C(Hybrid)を検討した上で「Phase 1 はシンプルさ優先で Option A」と書いていたが、実際に動かしてみると「本当にこのクエリの分類、毎回 LLM 呼び出しが要るのか?」という疑問が出てきた。

- latency: 集計1回に対して LLM 呼び出しが2〜3回走る、chunk 数が増えるほど無視できないコストになりそう
- 信頼性: 分類を間違えると(例: `handle_table_display` が本来 aggregation であるべきクエリを拾う)、後続の処理が丸ごとズレる
- 実務(SAP や他の Enterprise RAG)では、rule ベースの一次フィルタ + LLM は曖昧なケースのみにフォールバック、という Hybrid 構成が一般的なのでは?という予想はあるが、実際どうなのかは未検証

→ insights.md の Insight 02(Router 型 RAG)と直結する疑問。Phase 2 で Option C(Hybrid)に寄せる際に、実際の latency 計測と合わせて調べたい。

## 学び②: pandas の内部実装と `groupby` を使う理由

`sum_by_month` / `count_by_month` を実装する時、最初は素朴に `for receipt in receipts: ...` で月ごとに手動集計するコードを書こうとした。しかし pandas の中身は NumPy(さらに下は C)で実装されていて、`for` ループで1行ずつ Python で処理するより、`groupby` のような vectorized 操作の方が大幅に速いと知った。

データ件数が171件の今は体感できる差ではないが、「Python の for ループは遅い、pandas の組み込み演算に寄せる」という発想は今後データ量が増えたときにそのまま活きる設計判断だと思う。

### 今回使った関数まとめ

| 関数 | モジュール | 役割 |
|---|---|---|
| `pd.DataFrame(rows)` | pandas | dict のリストから DataFrame を構築 |
| `pd.to_datetime(df["date"])` | pandas | 文字列 → `datetime64` 型に変換 |
| `df.groupby("month")["total_eur"].sum()` | pandas | 月ごとに合計(for ループの代わり、内部は vectorized) |
| `df.groupby("month").size()` | pandas | 月ごとの件数 |
| `df.nlargest(n, "total_eur")` | pandas | 金額上位 N 件を抽出(`top_n_by_price`) |
| `df.to_markdown(index=False)` | pandas(+`tabulate`) | Markdown 形式の表に変換 |
| `df["date"].dt.strftime("%Y-%m-%d")` | pandas | datetime → 表示用の日付文字列(時刻を落とす) |
| `re.sub(r"\[cite:\s*\d+\]", "", text)` | re(標準ライブラリ) | citation artifact の除去 |
| `re.search(r"(?:トップ\|上位\|top)\s*(\d+)", query)` | re(標準ライブラリ) | 「トップN」をクエリから抽出 |
| `llm.invoke([SystemMessage, HumanMessage])` | langchain_google_genai | intent 判定・sub_intent 判定・自然文整形の3箇所で使用 |
