## 学び①: Aggregation failure の2段階分離(Day 10 の最大の学び)

素朴 RAG の集計クエリ失敗を、実データで **2 種類の異なる bottleneck** として分離できた。

### 第1段階: Retrieval bottleneck(top_k=50)

**症状**: 「月ごとの買い物回数と合計を出して」に対し、LLM が返した月別回数の合計がぴったり 50 に一致。2月は「1回」など、明らかに不自然な内訳。

**原因**: retrieval で 171 件から 50 件に切られる、LLM は渡された 50 件が「全体」だと信じて月別集計を実行、結果として **retrieval で偶然拾われた月ごとの断片数がそのまま LLM の回答になる**。

**診断法(応用可能)**: 「LLM の回答の合計 == top_k」が成立していれば、retrieval で切られている bug がほぼ確実。**LLM の回答から top_k を逆算できる**という気づきは他の RAG project にも応用できる。

**構造的限界**: top_k をどれだけ tuning しても、retrieval には「意味的に近いものを拾う」機能しかない、「全数を保証する」機能はない。集計の完全性(exhaustiveness)は retrieval の設計目標に含まれていない。

### 第2段階: Arithmetic bottleneck(top_k=all=171)

**症状**: top_k=len(split_docs)=171 に変更、LLM は全件を「見た」。総件数 171 は正しく答えた。しかし月別グルーピングを **10ヶ月中 9ヶ月間違えた**。

**Ground truth 比較**:

| 月 | 真の件数 | LLM回数 | 真の合計 EUR | LLM合計 EUR | 差 |
|---|---:|---:|---:|---:|---:|
| 2025-10 | 21 | 15 | 231.78 | 205.15 | -26.63 |
| 2025-11 | 23 | 22 | 307.52 | 355.85 | **+48.33** |
| 2025-12 | 12 | 15 | 177.98 | 201.21 | +23.23 |
| 2026-01 | 9 | 12 | 56.82 | 74.34 | +17.52 |
| 2026-02 | 8 | 9 | 54.33 | 57.38 | +3.05 |
| 2026-03 | 20 | 19 | 137.23 | 121.72 | -15.51 |
| 2026-04 | 21 | 22 | 124.69 | 153.30 | **+28.61** |
| 2026-05 | 17 | 16 | 107.55 | 125.79 | +18.24 |
| 2026-06 | 24 | 25 | 133.17 | 151.78 | +18.61 |
| 2026-07 | 16 | 16 | 143.48 | 150.36 | +6.88 |
| **合計** | **171** | **171** | **1474.55** | **1636.88** | **+162.33** |

**Ground truth 取得方法**:
```bash
for f in data/tuebingen/receipts_*.json; do
  echo "$f: count=$(jq 'length' $f), total=$(jq '[.[].transaction.total_eur] | add' $f)"
done
```

**原因分析**:
- 総件数 171 は保持できた = 全件が LLM の視野に入った証拠
- 月別グルーピングを 10ヶ月中 9ヶ月間違えた = **grouping/counting per bucket は transformer の本質的苦手領域**
- 誤差の方向が +/- ランダム = 「特定の月を見落とした」ではなく「純粋な計算失敗」
- 合計金額は systematic に過大(+162 EUR) = **LLM の算術には systematic bias がある**、production では信頼できない

**構造的限界**: LLM が全件を「読めた」としても、正確な集計は保証されない。transformer は自然言語生成に最適化されており、precise arithmetic at scale はアーキテクチャの得意領域ではない。

## 学び②: Router 型 RAG 必要性の実データ根拠が完成

Day 10 の 2 段階の実験で、素朴 RAG の限界を **層で分離して**言語化できるようになった:

| Query type | 素朴 RAG の挙動 | 適切な処理層 |
|---|---|---|
| Semantic(「Q-principle とは?」) | ✓ 動く | 既存 RAG pipeline |
| Aggregation, 小規模 window 内(「4月内最大値」) | △ top_k 依存で不安定 | RAG + top_k tuning |
| Aggregation, 全期間(「月別合計」) | ✗ 構造的破綻(retrieval + arithmetic 両方) | **SQL/pandas 決定的** |

**Router の存在意義**: 「retrieval と arithmetic の bottleneck を intent 判定で回避する」= Yamato のプロジェクトで実装すべき Week 3 の課題として、実データ根拠が固まった。

## 学び③: 「関数の入口で正規化する」パターン

`build_index` を `str | list[str]` に拡張する時、内部で毎回 isinstance 分岐すると読みにくくなる。**入口で1回だけ list 化して内部処理は list に統一**、これが Python の union 型を扱う定石。

```python
def build_index(filepaths: str | list[str]):
    if isinstance(filepaths, str):
        filepaths = [filepaths]
    # 以降 filepaths は必ず list[str]
```

責務分離の観点:
- 型の正規化 = 関数の入口の責務
- コア処理 = 単一型を前提にできる = 読みやすい
- 呼び出し側 = str でも list でも渡せる = 後方互換

## 学び④: マルチターン欠如の副次発見

`@cl.on_message` は毎ターン独立に呼ばれ、`generate_answer` に会話履歴を渡していない。ユーザが follow-up クエリ(「それぞれ何買った?」など)を投げると、「それぞれ」の指示対象が LLM に見えず、破綻する。

これは 3 種類の別問題の絡み合い:
1. 会話履歴の欠如(LLM の入力に前ターンが無い)
2. Retrieval の再実行問題(毎ターン独立に retrieval が走る)
3. 指示語の照応の破綻(anaphora resolution が切れる)

**理論マッピング**: Stalnaker の Common Ground が毎ターンリセットされる = 「会話」ではなく「単発 Q&A の連続」になっている。Week 3 で PostgreSQL 化する時、これは「Common Ground を永続化する」実装として位置づけられる。

## 学び⑤: Ground truth 検証の重要性(Applied AI Engineer の基本作法)

Flash Lite の月別集計回答を見た時、「もっともらしい」数字が並んでいたので、Yamato は最初「見えたけど計算間違い」と直感で判断した。実際に `jq` で ground truth を取ると、真の総件数は 171、LLM も 171、しかし内訳は全月で異なる、という **中間的な失敗パターン**が可視化された。

**教訓**:
- LLM が返す数字は「もっともらしさ」で判断してはいけない、外部検証が必須
- Aggregation クエリの検証は必ず ground truth 取得を含める
- Production ML では「LLM の回答を信じる前に、独立した pipeline で検証する仕組み」が必要
- 面接ネタ: 「LLM の集計出力を jq/pandas で照合する検証ステップを最初から挟むのが Applied AI Engineer の basic hygiene」

## 気づき / Theory Mapping への含意(Week 4 用ネタ)

- **Retrieval bottleneck と Arithmetic bottleneck の分離** = 素朴 RAG の失敗を「一括」ではなく「層別」に語れる状態。Applied AI Engineer の diagnostic skill として面接で差別化ポイント
- **Common Ground の Persistence** = マルチターン欠如は Stalnaker の Common Ground が session 内でリセットされる問題、`cl.user_session` は per-tab の Common Ground を保持するが、pipeline はそれを LLM に渡していない、これは「Common Ground の存在」と「Common Ground の運用」の分離
- **Router = QUD 型に応じた retriever 選択** = Roberts の QUD 理論では question type によって適切な answer strategy が決まる、Router はまさに「QUD type → strategy」の写像を実装する pragmatic 機構
- **LLM の Systematic bias** = 合計金額が +162 EUR 過大になった現象、これは加算タスクにおいて LLM が特定方向へ drift する observation、production ML の trustworthiness 議論に接続
