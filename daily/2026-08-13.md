## 学び①: RAG = Retrieval + Augmented + Generation の 3 段
**疑問**: cosine similarity で top-K chunks を取れた時点で「RAG 完成」と言える?

**答え**: **Retrieval が動いているだけ**、まだ 1/3 段階。
- **R (Retrieval)**: 質問に関連する chunks を取得(cosine)← 今日の前半で完成
- **A (Augmented)**: chunks を LLM のプロンプトに埋め込む ← 今日 20 行で実装
- **G (Generation)**: LLM が chunks を読んで回答生成 ← Day 1-2 の ChatModel が再登場

RAG の Generation 段は Day 1-2 の Gemini 呼び出しの応用でしかない。ただし **SystemMessage で「文脈のみを根拠に答えろ」の制約**を入れる = hallucination 抑制の実装的な芯。`temperature=0.3` に下げる = deterministic 寄り(RAG では低めが定石)。

## 学び②(重要): Semantic Gap の 2 種類 — Speech Act ミスマッチ と Chunk Size 希釈

**観察**: クエリ「Q-principle って何?」に対して、Q-principle chunk が top 3 に入らなかった。

**Retrieval 結果(top_k=5 拡張後)**:

| 順位 | Score | Header |
|---|---|---|
| 1 | 0.4510 | 背景: Grice から Neo-Grice へ |
| 2 | 0.4456 | R-principle(speaker 志向) |
| 3 | 0.4274 | 実装への含意(RAG 設計との接点) |
| 4 | 0.3857 | 未解決の疑問 |
| 5 | 0.3833 | **Q-principle(hearer 志向)** ← 求めていた chunk |

Q-principle chunk が 5 位まで落ちた原因を、Yamato が実際のノート内容と照らして 2 要因に分離:

**要因 1: Speech Act ミスマッチ**(昨日発見、今日実証)
- R-principle chunk には「Yamato のメモ」が入っていて、**定義的な問いへの答え形式**を持っていた → embedding が「Q-principle って何?」というクエリと近くなった
- BGE-M3 は Illocutionary Force(発話の型)の一致を Propositional Content(命題内容)より優先しがち
- **業界用語**: query-document semantic gap、intent classification の問題

**要因 2: Chunk Size 希釈**(今日新規発見)
- Q-principle chunk は本文が長い(定義 + 例文 + Horn scale 説明 + 補足)= すべて 1 chunk に入っていた
- 結果: ベクトルが「Q-principle 一点」ではなく「Q-principle 周辺の広い意味領域の平均」になった
- **specific なクエリに対して specific にマッチできない**
- **業界用語**: chunk size vs granularity trade-off

### 2 つの要因の分離と対処法

| 症状 | 原因 | 対処技術 | Yamato のプロジェクト該当週 |
|---|---|---|---|
| Speech Act ミスマッチ | Directive query が Assertive chunk を優先 | Query rewriting / HyDE | Week 2 頭 |
| Chunk size 希釈 | 長い chunk でベクトルが平均化 | Small-to-Big Retrieval / semantic chunking | Week 3 |

**Small-to-Big Retrieval**: 検索には細かい chunk(1-2 文)を使い、LLM に渡す時はその chunk が属する親 chunk(セクション全体)を渡す。**「検索の粒度」と「読ませる粒度」を分ける**。LangChain の `ParentDocumentRetriever` で実装可能、Week 3 で触る予定。

**HyDE (Hypothetical Document Embeddings)**: LLM に「もし答えがあるとしたらこう書いてある」という架空 chunk を書かせて、それで検索。Yamato の Speech Act 観察を構造的に解決する: クエリ(Directive)→ 架空回答(Assertive)→ 実際の Assertive chunk と一致する空間に来る。

**なぜ Yamato がこの分離を発見できたか**: Speech Act theory のフレームワーク + Yamato のノートの実際の中身を目視で照らし合わせたから。**理論と実装の橋渡しの実例**、Week 4 の theory-mapping の芯素材。

## 学び③: top_k を増やす判断が結果を変える
**疑問**: LLM が「情報がない」と答えた。パイプラインが壊れているのか?

**答え**: **壊れていない、LLM が正しく動いている**。Q-principle chunk が top 3 に入っていなかったので、LLM は正直に「情報がない」と答えた = SystemMessage の指示通り。

**対処**: `top_k=3` → `top_k=5` に変更。これで Q-principle chunk が 5 位で context に入り、LLM が正しく定義を返せた。

**LLM の Final Answer(正しく動作)**:
> Q-principle(聞き手志向)とは、「言えるだけ言え」という原則です。話者は情報的に強い表現を選ぶべきだとされており、聞き手が「話者がより強い表現を選ばなかったということは、その強い表現は成立していない」と推論することを指します(例:「some」→「all(すべての)ではない」と推論する尺度含意など)。

**判断の学び**: 
- **Retrieval の Recall を上げる = top_k を増やす**、ただしトレードオフあり(トークン消費増、無関係 chunk 混入リスク)
- **ユーザーにクエリを書き直させるのは UX として NG**、システム側で吸収するのが実務(query rewriting / HyDE が候補)
- 「?」を付けても順序は変わらず、スコアが 0.01 変わっただけ = 句読点も BGE-M3 は 1 トークン扱い、影響は小さい

## 学び⑤: Function 化と全体像のバランス
**Yamato の学習様式に合わせたルール**:

1. **探索フェーズ**: 1 つの .py にベタ書き、動作を先に見る(embed_test.py がこれ)
2. **整理フェーズ**: 動いてから Function に切り出し(rag_pipeline.py がこれ)

**Function 化の判定基準**:
- 2 回以上使う → Function
- 入出力が明確 → Function
- 1 回だけ、パイプラインの中で流れる → 直接書く

**docstring テンプレ**(コアな Function だけ):
- Input / Output / なぜ の 3 セクション

**全体像を保つコツ**:
- `__main__` を 3-5 行の目次として使う
- ファイル冒頭に Called by / Depends on の docstring
- 週 1 でアーキテクチャ図を書き直す

## 学び⑥: SAP Operation 職との会話で見えた業界地図
**疑問**: SAP で Working Student として働いている人が AI について話していて違和感、Yamato が遅れているのか?

**答え**: **遅れていない、話している「AI」の意味が違う**。現代の AI は 3 層構造:

| 層 | 誰が扱う | 例 |
|---|---|---|
| ユーザー層 | オペレーター、営業、事務 | ChatGPT でメール、社内 RAG ツール検索 |
| **エンジニアリング層** | **Ece さんクラス、Applied AI Engineer** | **LangChain で RAG、Postgres、LangGraph** ← Yamato のターゲット |
| 研究層 | ML Research、DeepMind、BAAI | 新しい embedding モデル訓練、Transformer 改良 |

**会社別の Speech Act 用語の使い方**:
- SAP 応用 / Google 応用: 業界用語(intent classification)にすぐ翻訳、理論はチラ見せ
- Google Research / DeepL / Aleph Alpha: 理論用語のまま深く議論
- **Yamato のプロジェクト = 上記全部に対応可能**(1 実装、話し方を会社ごとに変えられる)

**AI と折り合いをつけるルール**:
- **コア(タイピング)**: パイプラインの各ステップ、主要な設計判断、エラーのデバッグ経路、理論と実装のマッピング
- **周辺(丸投げ)**: .gitignore、boilerplate、コミットメッセージ、リファクタの機械部分
- **判断基準**: 「面接で『なぜこの実装?』と聞かれて答えられないコードは自分のリポジトリに残さない」
- **理解の 4 段階**: (1) 入出力言える、(2) 1 段下の呼び出し言える、(3) なぜこの選択か言える、(4) 実装の中身言える。**Applied AI Engineer なら 3 で十分**
- **Yamato の学習様式**: プロジェクトで手を動かして理論と実装が繋がった時に定着(Lasso/Ridge の経験と同じ)
