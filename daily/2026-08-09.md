## 学び①: Thought Signature の正体
**疑問**: LangChain 版の `response.content` に `extras.signature` という長大な base64 文字列が現れて戸惑った。これは何?

**観察**: gemini-3.5-flash に切り替えたタイミングで出現。生 SDK 版では見えていなかった。

**答え**: Gemini 3 系(および 2.5 系の一部)のレスポンスに含まれる **`thought_signature` = 暗号化された内部推論状態**。opaque な token で、人間は復号できない。
- 単発の応答なら無視して OK
- マルチターン(特に function calling)で送り返さないと 400 エラー or 推論品質低下
- LangChain の Gemini アダプタは `AIMessage` を履歴に含めれば透過的に扱う
- Week 3 の Postgres 永続化で `AIMessage.additional_kwargs` や content blocks を捨てないよう ADR に必ず記載

**関連: 「モデルの思考を見る」3 概念の区別**
1. **LangChain の `verbose=True`**: チェインが送るプロンプト・返る応答を print、デバッグ用、モデル内部は見えない
2. **Gemini の Thought Summary**(`include_thoughts=True`): モデル推論を**人間可読な要約**で返す。**これが「思考を見る」に該当**
3. **Thought Signature**(上記): モデル内部推論の**暗号化 token**、人間は読めない、次リクエストに渡すためのもの

## 学び②: response オブジェクトの木構造
**疑問**: `response.text` で本文が取れていたが、Thought Summary を出したら `candidates` や `parts` を扱う必要が出て、いきなり複数形が出て戸惑った。全体構造は?

**答え**: response は Pydantic の木構造。

```
response
├── candidates: list        ← 複数候補生成可能な仕様(OpenAI の choices 相当、デフォルト 1)
│   └── [0]
│       ├── content
│       │   ├── role
│       │   └── parts: list ← テキスト+画像+関数呼び出し+思考の混在対応
│       │       └── [i]
│       │           ├── text
│       │           ├── thought (bool)
│       │           └── function_call
│       ├── finish_reason
│       └── safety_ratings
├── usage_metadata
│   ├── prompt_token_count
│   ├── candidates_token_count
│   └── total_token_count
└── text: str               ← ショートカット
```

- `.text` の実体 = `candidates[0]` の全 part の text を連結して返す
- `include_thoughts=True` にすると part が「思考パート」と「回答パート」に分かれるので、明示ループが必要
- 確認方法: `print(response.model_dump_json(indent=2, exclude_none=True))` で全構造を可視化

## 学び③: モデルは英語で考えているのか
**観察**: 日本語で「今 LangChain 学んでるけど面白いね」と聞いたら、Thought Summary が **英語 → ローマ字下書き → 英訳 → 最終日本語出力** の 4 段階になっていた。

**疑問**: モデルは英語で考えている? トークン消費は増える?

**答え(半分そう、半分違う)**:
- 【そう】LLM 学習データは英語比率が圧倒的、Chain-of-Thought の訓練もほぼ英語データ、多言語モデル内部に「英語ハブ」的性質があると Google/Anthropic の研究で報告
- 【違う】モデルは概念空間で動作、特定言語で考えているわけではない。CoT は訓練で学んだ書き方であってモデル内部の演算そのものではない
- ローマ字下書き + 英訳併記の観察 = 訓練データ中でローマ字が現れるのはほぼ語学教材の文脈のみ →「ローマ字を書く時は英訳を隣に添える」という書き方の癖を学習した痕跡

**トークン消費テーブル**:

| モード | 消費構造 |
|---|---|
| 通常応答 | 質問 + 応答 |
| Thought Summary あり | 質問 + 思考(英語) + 応答(日本語) |
| 翻訳ドラフトも入る場合 | 質問 + 思考 + ローマ字下書き + 英訳 + 応答 |

- 無料枠 250 req/day は 1 リクエスト = 1 カウントなので影響なし、有料化時にコストで顕在化
- 節約 tip: system message で "Always think in the same language as the user's query" 指定で下書きレイヤーが減る(品質トレードオフあり)

## 学び④: 音声 AI での日本語 → 韓国語 drift 現象
**観察**: 音声 AI(Gemini)に日本語で話しかけたのに、時々韓国語で返されることがある。

**疑問**: この現象は何?

**答え**: **"language confusion" / "cross-lingual drift"** と呼ばれる多言語 LLM の既知現象。日韓ペアで特に起きやすい 3 要因:

1. **埋め込み空間で近い**: SOV 語順、助詞システム(は/が ↔ 은/는/이/가)、漢字語彙の同源語(도서관 = 図書館)、K-POP/韓流の bilingual コンテンツ学習
2. **音声認識側の曖昧さ**: 短い発話、雑音、あいまい母音で Language ID の confidence が下がると、近い言語が勝つ
3. **学習データの偏り**: 特定トピック(コスメ、料理、K-POP)で bilingual 混在データが多く、韓国語トークンの確率が上がる

**プロジェクトへの含意**(Week 4 の LLM Challenges research「multilingual retrieval」で書けるネタ):
- **Retrieval 側では強み**: BGE-M3 は多言語対応で日本語クエリ → 英語・独語ドキュメントもヒット、「言語間の滲み」が強みになる方向
- **Generation 側では弱み**: 同じ多言語性が意図しない言語 drift を招く。日英独の 3 言語で drift が起きうる(独語 → 英語、独語 → オランダ語混在など)
- **防御策**: (1) system prompt で言語を pin(REQUIREMENTS.md の「質問と同じ言語で返す」がまさにこれ)、(2) 生成後の Language ID チェックで違ったら再生成、(3) Retriever のソース言語を metadata で持って必要に応じて絞る

## 気づき / Theory Mapping への含意(Week 4 用ネタ)
- **Thought Signature は Common Ground の API 実装**として言及可能。Stalnaker の Common Ground、Gemini 3 の Thought Signature、LangGraph の State/Checkpointer、Session Store の Message history を並べて、**「同じ問題を異なる粒度で解いている」構図**として書ける
- **思考の可視化(Thought Summary)と保持(Thought Signature)は別の関心事**。片方は人間が読むため、片方はモデルが次ターンで自分に読み返すため。同じ内部状態を 2 つの粒度で外に出している
- **「言語間の滲み」は多言語 RAG 設計の表と裏**: retrieval では強み、generation では弱み、という対比が multilingual RAG の設計原理として書ける
- **英語ハブ現象と日韓 drift は同じ根**: 前者は意図的に英語を経由、後者は意図せず言語境界がずれる。どちらも「多言語表現空間で言語同士が綺麗に分かれていない」ことから来ている
