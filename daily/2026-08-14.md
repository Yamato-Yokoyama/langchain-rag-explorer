前提の共有

Yamato の現状の理解、まったく正しいです。今の Flat Retrieval:

[1] クエリを書く
       ↓
[2] クエリを embed
       ↓
[3] Corpus の chunks(12個)と cosine 計算
       ↓
[4] ランキングして top-K を取る
       ↓
[5] top-K chunks を Gemini に渡す
       ↓
[6] Gemini が context を読んで回答

これが Flat Retrieval(1 種類の chunk しかない)。今日の rag_pipeline.py がこれ。

「なぜ 2 段階にするか」の芯

Retrieval の粒度と Reading の粒度を分ける、これが Small-to-Big の全て。

	求められる粒度	現状(Flat)
Retrieval	細かい(specific にマッチ)	大きい chunk = 意味が薄まる
Reading (LLM)	大きい(文脈豊富)	大きい chunk = 良いが retrieval が犠牲

Flat Retrieval は「1 個の chunk で両方の要件を満たそう」として、どちらも中途半端になる。Small-to-Big は「別々に最適化しよう」という発想。

Yamato のノートで具体的に

現在の Q-principle chunk はこんな構造:

### Q-principle(hearer 志向)
「言えるだけ言え」— 話者は情報的に強い表現を選ぶべき。Q は聞き手のためのもの。

**例**: 「some students passed」→ 「not all students passed」の含意。

なぜか: もし全員合格していたら話者は "all" と言ったはず。"some" を選んだ = 
"all" は成立していない、と聞き手が推論する。これが **scalar implicature**。

Horn scale: `<all, most, many, some, few>` のような、情報の強さで並ぶ表現群。

Small chunks に分けると 4 つくらい:

small_1: 「言えるだけ言え」定義部分
small_2: 例文「some students passed」の部分
small_3: 「なぜか」の推論説明
small_4: Horn scale の説明

クエリ「Q-principle って何?」で最も specific にマッチする small_1 が 1 位に来る。その parent = セクション全体を LLM に渡すので、LLM は例文も scale も全部見て「定義 + 例 + Horn scale」の完全な回答ができる。

LangChain での実装イメージ(概略)

Week 3 で触るコード、雰囲気だけ:

python
from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore

# 2 種類の Splitter を用意
parent_splitter = MarkdownHeaderTextSplitter(...)         # 大きい chunk 用(既存)
child_splitter = RecursiveCharacterTextSplitter(          # 小さい chunk 用(新規)
    chunk_size=200, chunk_overlap=20
)

# Retriever が 2 種類の chunk を紐づけて管理
retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,      # small(child)chunks の埋め込みが入る
    docstore=InMemoryStore(),     # big(parent)chunks の実体が入る
    child_splitter=child_splitter,
    parent_splitter=parent_splitter,
)

# ドキュメント追加時に自動で: parent 分割 → child 分割 → child を embed → parent を store
retriever.add_documents([document])

# 検索時: child で検索 → parent を返す
retrieved = retriever.invoke("Q-principle って何?")
# retrieved は parent chunks(セクション全体)のリスト

LangChain が「small で検索、parent を返す」の対応管理を全部やってくれる。今 Yamato が手動でやっている「vectors と split_docs を i でペア管理」の、より高度な版と思えば近い。

落とし穴の予告

Small-to-Big が万能ではない理由:

Parent が大きすぎると LLM の context を圧迫: 巨大な章全体を parent にすると 1 chunk で 5000 tokens とかになる、他の候補が入る余地がなくなる
Small が細かすぎると誤マッチが増える: 「例:」だけの chunk が「例って何?」みたいなクエリで意味なくヒットする
重複除去のロジック: 上位 5 個の small が全部同じ parent だと、実質 1 個の chunk しか LLM に渡らない

これらを踏まえた parent と child の粒度設計が Week 3 のエンジニアリング判断。Yamato の 12 chunks の Neo-Gricean ノートだと、parent = セクション(H2)、child = 段落 or 文、が良さそう。
