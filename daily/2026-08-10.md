## 詰まったこと・調べたこと

### 1. `langchain-community` 廃止トラブル
- `pip install "langchain-community" "unstructured[md]"` の指示で `ImportError`
- 調査: langchain-community は 2026 年 6 月 19 日にアーカイブ済み、メンテ終了
- LangChain v1 方針で「1 プロバイダ = 1 独立パッケージ」に移行(`langchain-unstructured`, `langchain-chroma`, `langchain-huggingface` など)
- 対応: `langchain-unstructured` に切り替え、古いパッケージをアンインストール
- **面接ストーリーになる**: 「使おうとしたライブラリが応募の 7 週間前にアーカイブされていた、deprecation notice から migration path を辿った」

### 2. `UnstructuredLoader` が Markdown で崩れた
- 症状: Document count 1、page_content が YAML frontmatter だけ、category が `UncategorizedText`、languages が英語判定
- 原因: YAML frontmatter で Unstructured のパーサーが混乱、以降の本文が element 化されない + libmagic 未インストール
- **設計判断**: `UnstructuredLoader` は「Load + Split を一気に」を狙うが Markdown には向かない、**Load と Split を独立させる方が予測可能**
- 採用: 自作 `load_as_plain_text()`(4 行)+ `MarkdownHeaderTextSplitter` の組み合わせ

### 3. `MarkdownHeaderTextSplitter` の `mode` パラメータエラー
- 症状: `TypeError: MarkdownHeaderTextSplitter.__init__() got an unexpected keyword argument 'mode'`
- 原因: `mode` は `UnstructuredLoader` のパラメータで、`MarkdownHeaderTextSplitter` のパラメータではない
- 正しい書き方: `MarkdownHeaderTextSplitter(headers_to_split_on=[("#", "Header 1"), ("##", "Header 2"), ("###", "Header 3")])`
- 各タプル: 左が Markdown 記号(認識パターン)、右が metadata のキー名(格納先)

### 4. matplotlib の日本語文字化け
- `plt.rcParams["font.family"] = "Hiragino Sans"` では反映されない場合あり
- 解決: `pip install japanize-matplotlib` + import 直後に `import japanize_matplotlib` 1 行

## 学び①: RAG パイプラインの 3 層責任分担
**疑問**: Load → Split → Embed → Retrieve、これらは全部 LangChain が担当?

**答え**: 3 層に分かれる。
- **LangChain の担当**: 部品同士を繋ぐ共通インターフェース、既存ツールのラッパー
- **モデル/DB の担当**: 実際の重い処理(埋め込み計算、ベクトル保存、生成)
- **エンジニア(Yamato)の担当**: 戦略選択 — どう分割するか、どのモデルを使うか、どう検索するか

Day 1-2 で見た「ChatModel はプロバイダ差し替えだけで動く」の構造が、Loader / Embedding / VectorStore にも同じように適用されている。**LangChain はオーケストレーター、ML 計算そのものはやってない**。

## 学び②: Document / split_docs のリスト構造
**疑問**: `split_docs = splitter.split_text(docs[0].page_content)` の `docs[0]` の意味と、複数ファイルになった時どうなるか?

**答え**:

```
1 ファイルの時:
docs        = [Document(全文)]              ← index 0 だけ
split_docs  = [chunk0, chunk1, ..., chunk11]  ← 12 個

3 ファイルの時(QUD, Neo-Gricean, Speech Acts):
docs = [
    Document(QUD 全文),        # docs[0]
    Document(Neo-Gricean 全文), # docs[1]
    Document(Speech Acts 全文), # docs[2]
]
split_docs = [QUD の 8 chunks, Neo-Gricean の 12 chunks, Speech Acts の 10 chunks]
           = 30 要素のフラットなリスト
```

各 chunk の metadata に `source` が付いているから「どのファイル由来か」追跡可能。Load 時に自作関数で `metadata={"source": filepath}` を仕込んでいたのは Week 2 の複数ファイル化の伏線。

**Document オブジェクトは 2 属性だけ**: `page_content`(文字列)+ `metadata`(辞書)。属性アクセス(`.page_content`)と辞書アクセス(`["source"]`)の混在に注意。

## 学び③: なぜ Embedding が必要なのか
**疑問**: キーワード検索じゃダメなの?なぜ embed する必要がある?

**答え(4 つの理由)**:
1. **同義語で切れる**: 「Q 原則って?」で「Q-principle」がヒットしない
2. **日英クロスで完全に切れる**: 多言語検索の要件を直接壊す(REQUIREMENTS.md の核心)
3. **言い換え質問で切れる**: 「Horn の 2 分割は?」で Q-principle/R-principle が返せない
4. **意味的な関連が拾えない**: 「LLM の hallucination と含意理論」でネオグライスノートが返せない

**Embedding が何をやっているか**: BGE-M3 のような多言語埋め込みが、テキストを 1024 次元の密ベクトルに変換。この空間で「意味が近い文はベクトルが近い」性質を持つ = cosine similarity で検索可能。

**省略できる場合**: コーパスが極小(全部 context window に入る)、完全一致検索で足りる、など。Yamato のプロジェクトは多言語+意味検索が要件なので **必須**。

**業界のリアル**: 2025-2026 現在、BM25(キーワード)+ embedding(意味)のハイブリッドが最強、というのがコンセンサス。

## 学び④: Embedding の系譜
**チャート**:
```
one-hot (スパース、意味なし)
   ↓  次元削減(SVD/PCA または neural)
word2vec (密ベクトル、単語単位、意味あり、語順なし)
   ↓  Transformer/self-attention 導入
BERT (密ベクトル、文単位、意味あり、語順あり)
   ↓  対照学習 + 多言語
BGE-M3 (1024 次元、多言語対応、Yamato の使う実物)
```

**3 つのキーポイント**:
1. one-hot → word2vec で「意味を持たせる」(次元削減発想、SVD 直系または neural)
2. word2vec → Transformer で「語順を持たせる」(self-attention による可変重み)
3. 単語 → 文 → Doc の粒度で埋め込む対象が変わる、実装のインターフェースは同じ(テキストを渡して固定次元ベクトルが返る)

**BGE-M3 が素の BERT + embedding 用途 に加えている 3 点**:
- **対照学習**: 「意味が近いペアが近くなる」を明示的に訓練(素の BERT は Masked Language Modeling で embedding は副産物)
- **多言語対応**: 100+ 言語を同じ空間に(日本語「Q 原則」と英語 "Q-principle" が近くに)
- **長文対応**: 512 → 8192 トークン

「M3」= Multi-Functionality(dense/sparse/multi-vector)、Multi-Linguality、Multi-Granularity。

## 学び⑤: Embedding の選択、API 依存 vs ローカル(HF)の 2 択
**API 系(Google text-embedding-004, OpenAI 系)**: 従量課金、プライバシー懸念、ネットワーク遅延、オフライン不可

**ローカル(BGE-M3 via HuggingFace)**: 初回 DL 後は無料、完全ローカル、CPU 遅い/GPU 速い、オフライン可

**VSCode の autocomplete トラップ**: `ChatGoogleGenerativeAI().embed_documents(...)` は**クラスが違う**。チャット用 = `ChatGoogleGenerativeAI`、埋め込み用 = `GoogleGenerativeAIEmbeddings`。同じ Google でも別 API エンドポイント、別クラス。

**Yamato のプロジェクトの選択理由**:
1. プライバシー(LinkedIn 投稿・自己紹介・CV は個人情報、API に送りたくない)
2. 多言語ベンチマーク(BGE-M3 は日英独で強い)
3. 無料無制限
4. **面接ストーリー**: 「なぜ local?」の答えがプロジェクトの根本理由(プライバシー)と直結

**Enterprise の実務**: SAP 等では顧客データを外部 API に送れない制約が強い、ローカルモデル運用の経験は評価される = Ece さんプロファイルの enterprise 志向と揃う。

## 学び⑥: PCA、テスト結果の例で理解
**疑問**: 高次元をプロットできないから PCA で 2D に落とすのが定石?300 次元や 1024 次元のバラつきってどう理解する?

**答え**: PCA は「重み付き平均を賢く計算する道具」、Yamato の直感でやった「数学と物理の平均」を数学的に厳密にやっているだけ。

**5 人の学生の例**:

| 学生 | 数学 | 物理 |
|---|---|---|
| A | 90 | 85 |
| B | 75 | 70 |
| C | 60 | 55 |
| D | 45 | 50 |
| E | 30 | 35 |

5 人の点が右上がりに並ぶ = 数学と物理が連動。

**PCA が答える問い**: 「1 人を 1 つの数字で表すなら?」→ 数学と物理を混ぜた「総合指数」= PC1。

**Yamato の直感(平均)= 0.5 と 0.5** ≈ PCA の PC1(正確には 0.707 と 0.707、比率は 1:1)。今回は一致。

**PC1** = 一番情報量の多い方向(点が広く散らばる) = 分散が大きい方向
**PC2** = PC1 に直交する、次に散らばる方向 = PC1 で捉えきれなかった残り情報

**explained_variance_ratio_ は線形回帰の R² と同じ概念**:
- 線形回帰 R² = 96%: モデルの線が元データのばらつきの 96% を説明
- PCA PC1 = 96%: PC1 軸が元データのばらつきの 96% を説明
- 名前が違うだけ、**「全体のばらつきに占める割合」**は同じ

**なぜ PC1/PC2 は直交するか**: 同じ方向を向いていたら情報が被る = 意味がない。PC1 に垂直な方向の中から、次に散らばる方向を選ぶ。**役割分担している**。

**元の軸が相関 → 少ない PC で高い割合、独立 → 多くの PC が必要**

**BGE-M3 の場合**: 1024 次元を広く独立に使うよう訓練済み = 元々広く散らばっている = 2 軸に落とすと 33% しか取れない。これは **BGE-M3 の品質の証拠**であって、悪いことではない。

**このプロジェクトでの位置づけ**: RAG パイプラインには使わない(検索は元の 1024 次元で)、可視化専用。**面接での 1 段の答え**: 「PCA は可視化のためだけ、検索は元次元で行う」。

## 学び⑦: 可視化コード理解
`ax.scatter(X_2d[:, 0], X_2d[:, 1], s=100)`:
- `X_2d`: shape (12, 2) の numpy 配列(行=chunk、列=PC1/PC2 座標)
- `[:, 0]`: 全行の 0 列目 = PC1 値(x 座標)
- `[:, 1]`: 全行の 1 列目 = PC2 値(y 座標)
- `s=100`: マーカーサイズ

numpy 2D 配列は `[行の指定, 列の指定]` でカンマ区切り、Python の list スライスとは別物。

**ラベル選択の or 短絡評価**:
```python
label = doc.metadata.get("Header 3") or doc.metadata.get("Header 2") or doc.metadata.get("Header 1", f"chunk{i}")
```
Header 3(最も具体的)から順にフォールバック。chunk 位置により中身が変わる:
- 本文 chunk → Header 1/2/3 全部持つ → 3 が選ばれる
- YAML frontmatter や導入部 → Header なし → `f"chunk{i}"` にフォールバック(chunk0 の正体)

## 気づき: PCA プロットが BGE-M3 の品質を視覚的に証明
文字化けを直した PCA 2D プロットで、意味クラスタが確認できた:

- **Q-heuristic と I-heuristic が左上で近い**: 両方 Levinson の同節、hearer 志向 → **意味的正しい**
- **Q-principle と R-principle が中央で近い**: Horn の 2 原則、対概念 → **意味的正しい**
- **M-heuristic は Q/I と方向は同じで少し離れる**: Levinson 系だが性格が違う → **正しい**
- **Horn (1984) と Levinson (2000) が右端で近い**: 両方「著者名+年」の chunk、**文体が似ている**(意味ではなく文体で近くなった) → **面白い観察、面接ネタ**
- **chunk0(YAML frontmatter)は下端で孤立**: 本文と内容が違うから当然 → **正しい**

説明分散 PC1 18.3% + PC2 15.2% = 33.5% = BGE-M3 が 1024 次元を広く使えている証拠。
