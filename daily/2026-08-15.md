## 学び①: 3 種類の Semantic Gap を実データで観察
**疑問**: レシート JSON をコーパスに加えて自然言語クエリを試したら、なぜ 3 種類の失敗パターンが出たか?

**観察された 3 種類の gap**:

### Gap 1: 集計不能 (Aggregation Gap)
- クエリ: 「4 月の一番高い買い物は?」
- 症状: LLM が top-5 の中の一番高いもの(11.55 EUR)を「4 月の最高額」と答えた、実際には 12.90 EUR がある
- 原因: RAG は top-K しか見ない、全レコードの比較・集計は構造上できない
- 対処: SQL 層が必要、Week 3 の Postgres 移行で解決 → **Router 型 RAG の実装動機**

### Gap 2: 指示性の Gap (Referential Gap)  
- クエリ: 「留学生はどんな食べ物を買ってる?」
- 症状: retrieval は正しく取れた(Lidl レシート top-5)が、LLM が「情報がありません」と答えた
- 原因: SystemMessage「文脈のみを根拠に」が厳しすぎ、「留学生」という主体が document に明示されていないため LLM が拒否
- 対処: 
  - SystemMessage 緩和(「文脈を参考に、合理的推論可」に変更) → 効果あり
  - Query Contextualization(ユーザー背景を query に注入)
  - Data Enrichment(document に文脈を注入)

### Gap 3: スコア接近 (Score Convergence)
- クエリ: 「スーパーで何を買ってる?」
- 症状: top-5 の score が 0.50, 0.49, 0.49, 0.48... と接近、順位が意味を持たない
- 原因: レシートの page_content が短い + 抽象クエリで、BGE-M3 がどれも同程度に関連と判断
- 対処: chunk 統合(月単位サマリを追加)、chunk size 調整
- **判断**: 今回は許容範囲、LLM が top-5 から詳細リスト生成できたので実害なし

## 学び②: RAG の Context 問題への 2 種類の対処法

**問題**: 「留学生」等の暗黙のユーザー背景情報が document に無いと、LLM は文脈を補ってくれない。共有前提(Common Ground)を陽に与える必要がある。

### 対処 1: Query 側 = Query Contextualization
ユーザー情報を踏まえて query を拡張してから retrieve。

```python
# 使い方
user = {"nationality": "日本", "location": "Tübingen", "status": "留学生"}
expanded = contextualize_query("留学生はどんな食べ物?", user, llm)
# → "Tübingen で生活する日本人留学生の食事、購入品目、生活費データ"
```

### 対処 2: Document 側 = Data Enrichment / Metadata Augmentation
Document に文脈を注入してから index を作る。

```python
def _format_receipt_as_text(receipt: dict) -> str:
    header = "【Tübingen で生活する日本人留学生 Yamato の生活費記録】\n"
    header += f"{date}、{store_name}で..."
    return header
```

### 対処 2 種の比較表

| 対処 | メリット | デメリット | 選ばれる場面 |
|---|---|---|---|
| Query 側 (Contextualization) | Document は変えない、既存 index 再利用可能 | ユーザーごとに query 処理が変わる、personalization コスト | ユーザーが多い、Document が固定 |
| Document 側 (Enrichment) | 一度 index を作れば速い、全 query で恩恵 | Document 数だけ enrichment 処理、再インデックス必要 | ユーザーが少ない、Document が変わる |

### SAP / Enterprise での実例

**Query Contextualization の実例**:
- 顧客サポート RAG: 「私の契約はいつ切れる?」→ ログインユーザーの契約 ID を自動で query に埋め込む
- 社内 wiki 検索: 部署・役職を自動で context に足す(エンジニアが「稟議書の書き方」を聞いたら、エンジニア向けフォーマットを優先)
- 医療系: 患者 ID・年齢・性別を query に混ぜて患者固有情報を retrieve

**Data Enrichment の実例**:
- 契約書 chunk の冒頭に「この契約書は 顧客 X との 2024 年契約です」を毎回付ける
- Slack メッセージ chunk に「これは #engineering チャンネルの 2026 年 8 月の会話です」を追加
- 顧客サポートログの各 entry に「顧客の会員ランク: Gold」を注入

### Yamato のプロジェクトへの適用

- ユーザー = Yamato 1 人(personalization コストゼロ)、Document = レシート(増えていく)
- **今日は Document 側を先に実装**、1 回の loader 変更で全 chunk に恩恵
- 効果検証: 「留学生はどんな食べ物?」で score 0.50 → 0.60 に改善確認
- **学び**: Enrichment の 1 行注入で明確な改善、コスト対効果が高い

### Enrichment の副作用(要 Week 2-3 検証)

- 全 chunk に同じテキストが入る = **その部分だけで chunks 同士が類似**する
- 「留学生」を含むクエリで全レシートが同程度に high score になる、**順位付けが弱くなる可能性**
- 「Tübingen の Lidl」というクエリで、Tübingen 情報が全 chunk にあるので **店名の差別化が薄まる**
- **バランス**: 冒頭に少しだけ入れるのは OK、chunk 全体の 30% を占めるほど入れると差別化が壊れる

## 学び③: Yamato の JSON スキーマは実務向き

**Claude が最初に想定していたフラット構造 vs Yamato の実際のネスト構造**:

| 要素 | Claude 想定(初心者向け) | Yamato の実データ(実務向き) |
|---|---|---|
| store | 文字列 1 個 | `{name, address}` の dict |
| 日付・金額 | receipt 直下 | `transaction` に集約 |
| 品目名 | `name` 1 個 | `name_original` + `name_jp` の 2 言語 |
| 価格 | float 1 個 | `{regular_eur, discount_eur, final_eur}` |

**なぜ Yamato の構造が優れているか**:
- `store.address` 分離 → 同じ店の別支店を区別可能
- `transaction` まとまり → SQL の 1 行に対応しやすい
- `name_jp` と `name_original` 分離 → 日本語検索と原言語検索を両方できる、多言語 RAG で強い
- `price.regular_eur` と `final_eur` 分離 → 割引額計算可、「割引率が高い月は?」のクエリに答えられる

**学び**: Gemini 画像パースで自然に出てきた構造でも、実務レベルのデータ設計になっていた。**変えなくていい、このスキーマで進める**。

## 気づき / Theory Mapping への含意(Week 4 用ネタ)

- **RAG の Context 問題は Common Ground の欠如そのもの**: Stalnaker の Common Ground 理論では、対話者間で共有される前提の集合が必要とされる。RAG の chunks が Common Ground を持たない = LLM が「留学生」等の暗黙情報を補えない。**Data Enrichment / Query Contextualization は Common Ground を陽に構築する技術**として位置づけられる
- **3 種類の Semantic Gap の分離**: (1) Speech Act ミスマッチ(Day 5)、(2) Chunk Size 希釈(Day 5)、(3) 指示性 Gap(今日)、(4) 集計不能(今日)、(5) スコア接近(今日) = 素朴 RAG の限界を実データで 5 種類観察できた状態
- **RAG は「単一パイプラインで全部やろうとする」から失敗する**: 集計は SQL、意味検索は semantic、キーワード完全一致は BM25、と Router で振り分けるのが Enterprise の実像
- **Data Enrichment の副作用は Grice の Quantity Maxim と接続**: 全 chunk に同じ情報を注入すると「情報の識別性」が下がる = 過剰な冗長性は Quantity Maxim 違反、と読める
