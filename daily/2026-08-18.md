## 詰まったこと・調べたこと

### 1. `ModuleNotFoundError: No module named 'src'`
- 症状: `chainlit run src/chainlit_app.py` で import 失敗
- 原因: chainlit は `src/chainlit_app.py` を単体スクリプト扱い、sys.path の先頭に `src/` が入る、プロジェクトルートは入らない
- 対処: `PYTHONPATH=. chainlit run src/chainlit_app.py -w` で実行
- **教訓**: パッケージ import は「実行位置」ではなく「sys.path」で解決される、Week 3 で `pyproject.toml` + `pip install -e .` で恒久解決予定

### 2. Aggregation クエリで 3 回とも別の答えが出た(素朴 RAG の限界を実データで確認)
- 症状: 「4月一番高い買い物は?」「高い順ランキング」「品物も」の 3 クエリで、それぞれ 10.38 / 4.93 / 5.2 EUR と別の chunk がトップに来た
- 原因: top_k=5 で全 40 件のうち 5 件しか LLM に渡さない → クエリ表現のゆらぎで top 5 の中身が変わる → LLM は渡された 5 件の中の max を「一番高い」と答えるしかない
- 対処: top_k=50 で全件を LLM に渡すことで構造的に解決
- **教訓**: aggregation クエリは retrieval 改善では原理的に解けない、全件視認が必要、これが Router 必要性の実データ根拠

## 学び①: `cl.user_session` = per-user scope
Python のスコープに Web app 特有の 4 つ目の層が加わる:

| スコープ | 生存期間 | 共有範囲 |
|---|---|---|
| ローカル変数 | 関数実行中 | 誰とも共有しない |
| クラス属性 | インスタンス生存中 | インスタンス保持者 |
| グローバル変数 | プロセス生存中 | 全ユーザ ← Web だと危険 |
| **`cl.user_session`** | **ブラウザタブ生存中** | **そのタブのユーザだけ** |

`@cl.on_chat_start` と `@cl.on_message` は別関数なので、Python のスコープ規則ではローカル変数を共有できない。グローバル変数にするとマルチユーザ環境で漏洩リスク。Chainlit が WebSocket 接続 ID をキーに session dict を自動振り分け、`cl.user_session.set/get` で複数の値を key-value で預けられる。**Web app 特有の boilerplate を吸収してくれる**の中身の 1 つ。

## 学び②: Chainlit の正体 = FastAPI + WebSocket + React の thin wrapper
- **uvicorn**: ASGI サーバ、プロセスを起動
- **FastAPI**: HTTP/WebSocket ルーティング、uvicorn の上で動く
- **Chainlit**: 上記に **React 製の chat frontend** + **デコレータ API** + **セッション管理** + **Step/Element UI 部品** をパッケージ化

raw FastAPI で同じものを作るなら、frontend の React 実装、cookie/session、Markdown レンダリング、ファイルアップロード UI、CORS 設定などを数週間かけて書く必要がある。Chainlit はそれを **デコレータ数個 + cl.user_session + cl.Step** に圧縮している。

**面接での 1 文**:「Chainlit は FastAPI + WebSocket + React の thin wrapper で、UI boilerplate を書かずに RAG のロジックに集中できました。2025年5月にコミュニティメンテナンス移行したので production では Reflex や custom React + FastAPI も候補ですが、プロトタイプでは最速でした」

## 学び③: Aggregation failure と Router の関係を正しく分離
Yamato が最初に混同していた 2 つの問題を分離:

| 問題 | 内容 | 対処 |
|---|---|---|
| **Retrieval の順位ブレ** | クエリ表現のゆらぎで top 5 の中身が変わる | query rewriting, top_k 増加 |
| **集計不能(本質)** | 5 件しか渡してないから全 40 件から max を取れない | 全件視認 or SQL/DataFrame 併用 |

**Router が必要な理由は後者**。Retrieval を改善しても集計は解けない。**Retrieval 改善と Router 導入は直交する話**。

## 学び④: 「rewriting のおかげで精度が上がった」の因果誤帰属を回避
実験結果(top_k=50 + rewriting=True で正答)から素朴に「rewriting が主犯」と結論しがちだが、本当の主犯は top_k=50。理由: 全 40 件を LLM が視認できるようになったから集計が原理的に可能になった。rewriting は retrieval の順位安定性に効いたが、集計を可能にしたのは top_k。

**次回実験で切り分ける**: top_k=50 + rewriting=False で同じクエリ、正答が出れば「集計の主犯は top_k」確定。

**面接での正しい言い方**: 「top_k=全件で集計を可能にした + rewriting で retrieval を安定させた、2 層の改善」

## 学び⑤: Rewriting はデフォルト ON、ただしトレードオフを認識
人間はスペルミス・音声入力の誤字が普通にある、業務システムで rewriting をデフォルト ON にする判断はコスト vs 精度のトレードオフとして工学的に正しい。ただし本番スケールでは:
- Pro: recall 向上、typo 吸収、phrasing ゆらぎ吸収
- Con: LLM 追加呼び出し(latency + cost 増)、rewriting 自体がクエリ意味を drift させるリスク
- 妥協案: 安価な classifier でクエリを分類、rewriting が必要な場合のみ実行

Yamato の現スケールでは default-ON で問題なし、production 移行時に再検討。

## 気づき / Theory Mapping への含意(Week 4 用ネタ)

- **`cl.user_session` = per-user Common Ground**:Stalnaker の Common Ground を「対話者間の共有前提集合」と定義すると、`cl.user_session` は「特定のユーザとシステムの間の共有状態」で **per-user Common Ground の技術的実装**と読める。Week 3 で PostgreSQL 化する時、同じ概念が persistent Common Ground に拡張される
- **Aggregation failure = QUD 型ミスマッチ**:「一番高いのは何?」は QUD 上「集合内の要素順序を問う」型の質問。RAG は「関連する情報の想起」型の質問向けの設計、QUD 型が違うから構造的に解けない。**Router = QUD 型判定 + retriever 振り分け**と読み替えられる
- **rewriting = Grice の Manner Maxim 補正**:ユーザの typo・省略・曖昧語を LLM が「規範的な明瞭な表現」に書き直す = 話者の Manner Maxim(be perspicuous)違反をシステムが事後補正している。**pragmatic repair 機構**として位置づけられる
