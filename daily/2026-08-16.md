## 詰まったこと・調べたこと

### 1. Git ブランチ運用の混乱
- `git checkout -b feat/week1-rag-pipeline` を実行したはずが、`git branch -a` に main しかなかった
- 7 コミットが全部 main に直接乗っていた
- **判断**: 1 人プロジェクトのため実害ゼロ、`git push origin main` で決着、ブランチ切り直しはコスト対効果が悪い
- **教訓**: 「feat/xxx というブランチ名」と「Conventional Commits の `feat:` prefix」は別物、綴りが同じで混同しやすい
- **翌日以降の運用ルール**: 毎日作業開始時に `git checkout -b feat/day-XX-<内容>` を切る、作業終わりに push + PR + merge の 9 コマンドサイクル

### 2. Python 3.14 の venv で Chainlit が起動しない
- 症状: `anyio.NoEventLoopError: Not currently running on any asynchronous event loop`
- 原因: Python 3.14(2025 年 10 月リリース)が新しすぎて、Chainlit の依存(anyio, uvicorn)が完全対応していなかった
- 対処: `mv .venv .venv-py314-backup` で退避、`python3.11 -m venv .venv` で再構築、`sed` で loose requirements 作成、一括 install
- **教訓**: 「新しい方が良い」の直感が実務では逆に働くことがある、Python バージョン選択は依存パッケージの互換性まで見る

### 3. Chainlit が起動したのに Directory listing が出る
- 症状: ブラウザで localhost:8000 を開くと Yamato の別プロジェクトのファイル一覧が表示された
- 原因: 過去に `python -m http.server` を起動してターミナルを閉じていた、ゾンビプロセスが 8000 番を握っていた
- 対処: `lsof -ti :8000 | xargs kill` で古いプロセスを止める、Chainlit を再起動
- **教訓**: サーバーを立てたら必ず Ctrl+C で止めてからターミナルを閉じる

### 4. requirements.txt が古かった
- Chainlit も sentence-transformers も requirements.txt になかった
- 原因: 過去の `pip freeze` タイミングが早すぎ、以降の install が反映されていなかった
- 対処: 古い venv から `pip freeze > requirements-py314.txt` で export、loose 版に変換して一括 install、Chainlit 等を個別追加、最後に `pip freeze > requirements.txt` で更新
- **教訓**: `pip install XX` した日は必ずその日のコミットに requirements.txt の更新を含める、マイクロマネジメント方針に組み込む

## 学び①: GitHub workflow の実践(9 コマンドサイクル)
**疑問**: 実務で毎日どうやってブランチ運用するのか?

**答え**: 1 日 = 1 ブランチ = 1 PR、9 コマンドで完結:

```bash
# 朝: 作業台を出す
git checkout main
git pull
git checkout -b feat/day-XX-<内容>

# 日中: 適宜 add + commit(小さく)

# 夕方: 送る + 依頼書 + マージ + 片付け
pip freeze > requirements.txt   # install した日は必ず
git push -u origin feat/day-XX-<内容>
gh pr create --title "..." --body "..."
gh pr merge --merge --delete-branch
git checkout main
git pull
```

「Pull Request」の "pull" は git pull じゃなく「あなた(main の管理者)が僕の branch を pull してマージしてください」の依頼書。1 人プロジェクトでも PR を通す価値は: GitHub 上で変更内容が綺麗に diff 表示される + コミット履歴と紐づく + 面接官が見た時に実務経験の証拠になる。

## 学び②: venv とディスク管理の実感
**疑問**: 仮想環境に毎回 pip install していると、ローカルのどこに入っているのか?どんどん重くなるのか?

**答え**:
- 各 venv は **プロジェクトフォルダ内の `.venv/`** に丸ごと入る
- プロジェクトごとに完全独立、他のプロジェクトに影響しない
- 典型サイズ: BGE-M3 + torch + Chainlit で 1-2GB(Yamato の Python 3.14 venv は 1.5GB)
- **HuggingFace のモデル本体は `~/.cache/huggingface/hub/` に別置**、venv を消してもモデルは残る
- venv は消しても `pip install -r requirements.txt` で復元できる = だから requirements.txt を維持する

**Yamato の場合**:
- `.venv` 528M(Python 3.11、まだ軽い)
- `.venv-py314-backup` 1.5GB(削除予定、1.5GB 解放)

## 学び④: Python の型ヒント(Java/C 経験者向け)

**疑問**: Python では `message: cl.Message` と書けば、Java/C のようにオブジェクトが形成されると思っていたが、そうではない?

**答え**: **Python の型ヒントは「注釈」= コメントの延長**、実行時には何もしない。

**Java / C**: 型を書くこと = メモリ確保・オブジェクト生成、これがセット。
```java
Message msg = new Message("hello");  // 宣言と生成が一体
```

**Python**: 型ヒントとオブジェクト生成は分離。
```python
msg: cl.Message = cl.Message(content="hello")
#    ─────────────  ─────────────────────────────
#    型ヒント(ラベル)  オブジェクト生成(本体)
```

**型ヒントの 3 つの目的**:
1. VS Code の IntelliSense を効かせる(`message.` で属性一覧が出る)
2. ドキュメントとして(関数シグネチャで入出力が読める)
3. 静的解析ツール(mypy, pyright)で実行前チェック

**書く場所の慣習**: 引数と戻り値には書く、ローカル変数は省略が多い。

## 学び⑤: async / await とデコレータ

**疑問**: async / await の使い分けと、デコレータの本質は?

**答え(async / await)**:
- **`async def`**: この関数は非同期関数、内部で await を使うなら必須
- **`await`**: 実際にここで待つ指示、待ってる間に他の非同期タスクが並行して動く
- **判断基準**: 「時間かかる処理(ネット通信、DB アクセス、LLM 呼び出し)を含むか?」→ Yes なら async、No なら普通の def

**非同期の効果**: Chainlit / FastAPI は同時に複数ユーザーを扱う必要があるため必須。ユーザー A の LLM 呼び出し(3 秒)中に、ユーザー B の処理を並行できる。

**答え(デコレータ)**:
- **本質**: 関数の上に「役割ラベル」を貼る + 追加処理を挟む
- **`@cl.on_message`**: 「この関数はメッセージ受信時に呼ぶ」を Chainlit に登録
- **他のデコレータ**: `@cl.on_chat_start`(開始時)、`@cl.on_stop`(停止時)、`@cl.on_settings_update`(設定変更時)
- **FastAPI の CRUD 対応**: `@app.get`, `@app.post`, `@app.put`, `@app.delete`

**共通パターン**: 両者とも「デコレータで関数の役割を宣言する」= Yamato の「色ごとに分ける」直感が正確。

## 学び⑥: `cl.Message` の型の使い方(送受信両方)

**疑問**: `cl.Message` は Chainlit のメッセージを受け取って描画するタイプ?

**答え**: `cl.Message` は「メッセージオブジェクト」を表すクラス、方向は関係なし。

**使い方 A(受信)**: 関数の引数として、Chainlit から渡される
```python
async def handle_message(message: cl.Message):
    content = message.content  # ユーザー発話
```

**使い方 B(送信)**: 新規作成して .send() で送る
```python
await cl.Message(content="返信").send()
```

**比喩**: 手紙という物体は 1 種類、受け取る時も送る時も同じ構造(封筒、便箋、宛名、本文)、方向は使い方次第。
