## 「1つのAPI呼び出し(マルチモーダル)でいいじゃん」への回答

これは実際にいい質問で、**「複雑さが小さいうちは、その通り」**が正直な答え。1つの呼び出しで済むタスクを、無理にマルチエージェント化する必要はない。ただし、タスクが複雑になると1つの呼び出しでは崩れ始める理由が3つある。

### 理由1: 「1つの呼び出しに複数の仕事を詰め込む」と、Chunk Size希釈と同じことが起きる

これは既にあなたが自分で発見済みの問題と同じ構造。Neo-Griceanノートで「1chunkに定義+例+補足を全部詰め込むと意味が薄まる」という現象を見つけたのと同じことが、**プロンプトのレベルでも起きる**。「画像から抽出して」「抽出した内容が正しいか自己チェックして」「フォーマットも整えて」を1つのシステムプロンプトに詰め込むと、どれも中途半端になりやすい。1つの仕事に集中させた方が、その仕事の精度は上がる。

### 理由2: 自己チェックは「同じ文脈の中」だと機能しにくい

今日実際に起きたこと: `receipt_mcp_server.py`は1回の呼び出しで抽出だけをやり、**その出力が正しいかどうかは、あなたが人間として、別途PDFを見直して確認した**。これはまさに「抽出役」と「検証役」を分けていたということ。もしGemini自身に「抽出した直後に、同じ会話の中で自己採点して」と頼んでも、**自分がさっき出したばかりの答えに引きずられて、間違いに気づきにくい**(これはLLMの既知の傾向で、Anthropicの研究や業界でも"self-critique in the same context is weak, in a fresh context is stronger"として知られている)。検証を**別の呼び出し(別の文脈)**にすることで、この「自分の答えへの引きずられ」を減らせる。

### 理由3: 権限・ツールの範囲を分けられる(このプロジェクトの求人と直結)

1つの巨大なエージェントに「画像を読む」「ファイルに書き込む」「外部APIを叩く」を全部持たせると、何かがおかしくなった時の被害範囲(blast radius)が大きい。役割ごとに分けて、**それぞれに必要な権限・ツールだけを渡す**のが安全設計の基本(least privilege)。これはSecurity Patch QAチームの実務の発想そのもの。

## 「multi-agent = オーケストレーションが要るという意味」で合っているか

**合っている。** ただし線引きが1つある。今日、レシート3枚を順番に`extract_receipt`で処理したのは、**multi-agentではない**。同じ役割(抽出役)を3回繰り返しただけで、役割間の連携も無い。

multi-agentと呼べるのは、**役割が違う複数の呼び出しが、互いの出力を踏まえて動く**時:

| | 今日やったこと(3枚のレシート処理) | これから作るもの(criticノード) |
|---|---|---|
| 役割の数 | 1つ(抽出役)を3回繰り返し | 2つ(抽出役→検証役) |
| 連携 | 無し(3回は独立) | 有り(検証役は抽出役の出力を見て動く) |
| これは何か | ただのバッチ処理 | multi-agent |

なので「複数回呼ぶこと」自体はmulti-agentの条件ではなく、**「違う役割が、互いの出力をやり取りしながら、その連携をオーケストレーション(LangGraphのようなもの)が管理する」**のがmulti-agentの核心、という理解で合っている。

## 個人規模のプロジェクトでも役割分担の恩恵はあるのか

ある。ただし恩恵の種類が、企業規模の話とは少し違う。今日の実例がそのまま答えになっている:

- 今日、9/03のレシートで「ぶどう糖0.85€ではなく1.70€になっている」という誤りに**あなた自身が気づいた**。これは事実上、あなたが「criticの役割」を手動で果たしたということ
- criticノードを追加するというのは、**この「あなたが毎回手でやっている確認作業」を、もう1つの別のLLM呼び出しに肩代わりさせる**という話
- 個人規模では「組織の分業」という恩恵は関係ない。恩恵は単純に**品質(誤りを自動で拾えるか)**の話になる

正直なところ、全てのタスクでこれをやる必要はない。「間違えるとコストが高い・間違いに気づきにくいタスク」(今回のレシートのような、数字の読み違いが後で家計簿全体に響くもの)では価値が大きく、「間違えても大した影響がない単純なタスク」では、1呼び出しで十分なことも多い。

## なぜ大きい会社(SAPなど)でホットな話題なのか、実例

3つ、実例を挙げる。

**1. Anthropic自身が実際に使っている構造**: Anthropicの"multi-agent research system"(Claudeのresearch機能)は、1つの「orchestrator」エージェントが、複数の「subagent」を並列に立ち上げて、それぞれ別の角度から調査させ、最後に統合する設計になっている。実はこの会話の中で使っている`Agent`ツールの`fork`(このセッション自身を複製して並列に別タスクをやらせる仕組み)も、全く同じ発想の実装。「大きな1つの仕事を、独立した複数のsubagentに分担させて、最後に統合する」というパターンは、既に実際のプロダクトの中核になっている。

**2. 並列化によるレイテンシの削減**: 今日「レシート3枚の処理、結構時間かかった」と感じたと思うが、これは**3回を順番に(直列で)処理した**から。もしorchestratorが3つのsubagentを**並列に**立ち上げて同時に処理させていれば、体感時間は1回分に近くなっていたはず。企業規模でタスク量が増えるほど、この並列化の恩恵は大きくなる。

**3. セキュリティ・権限分離(この求人に直結)**: 大企業では「1つの万能エージェントに全部の権限を持たせる」のはリスクが高すぎる(本番環境への書き込み権限、顧客データへのアクセス、外部APIの呼び出し、を全部1つのエージェントに持たせると、誤動作や誤った指示への被害が甚大)。役割ごとにエージェントを分けて、それぞれに必要最小限の権限・ツールだけを与える、というのは、まさにSecurity Patch QAのようなチームが重視する設計思想そのもの。「なぜmulti-agentか」を面接で聞かれたら、品質(理由1・2)とセキュリティ(理由3)の両方を挙げられると強い。
