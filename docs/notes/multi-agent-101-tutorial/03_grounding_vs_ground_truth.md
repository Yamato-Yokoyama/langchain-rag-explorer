# Multi-Agent 101: criticは「正解」を知らない — groundednessという考え方

> `02`の続き。「criticは具体的に何を確認しているのか、自分も答えを知らない質問はどうするのか」への回答。

---

## 核心: criticは「客観的に正しいか」を判定できない

これが一番大事な訂正。criticも所詮LLMなので、**世界の真実を知っているわけではない**。「DeepLのVPは誰か」という質問に、criticが独自に正解を知っていて答え合わせをしてくれる、という仕組みではない。

criticが実際にできるのは、もっと地味なこと: **「回答が、実際に検索で引っ張ってきたデータ(retrieved_context)の中身とちゃんと一致しているか」**という、答え合わせではなく**照合**。これなら、criticも人間も「本当の正解」を知らなくても機械的に判定できる。

## あなたの1つ目の例: 「DeepLのVPは?」と「全く覚えていない繋がりの人」

- 「DeepLのVPは?」: あなた自身、LinkedInの繋がりを覚えているので、回答が合っているか目視できる。この場合、criticが無くても人間が検証できる
- 「全く覚えていない繋がりの人」「総当たりで全部の会社のVPは」: あなた自身も正解を知らない。この場合、**人間の目視チェックも機能しない**。まさにcriticの本領はここ

後者のケースでcriticが確認するのは「回答の中身が、実際に検索でヒットしたLinkedInデータ(`retrieved_context`)の中に書かれているか」だけ。もし検索結果に该当の会社の繋がりが1件もヒットしていないのに、回答が自信満々に「〇〇さんがVPです」と名前を挙げていたら、**それは検索結果に無い情報を作文している(=幻覚)**、とcriticが機械的に判定できる。「正しい名前を知っている」必要は無く、「検索結果に書いてあるかどうか」を照合するだけでいい。

この場合の正しい振る舞いは、「正解を当てる」ことではなく、**「検索結果からは十分な根拠が見つからなかった、と正直に言う」**こと。criticの役目は、根拠のない自信満々な回答を、正直な「わかりません」に修正させること。

## あなたの2つ目の例: 「11月12月の決算はいくらだったか」

これは実はこのプロジェクトでは事情が違う。`aggregation`ブランチ(集計クエリ)は、LLMが自由に数字を作文しているのではなく、**pandasの決定的な計算**(`sum_by_month`など)がやっている。同じデータに対して同じ計算をすれば、毎回**必ず同じ数字**が出る(LLMのように「毎回微妙に違う数字」にはならない)。なので`aggregation`ブランチにcriticは要らない、というのが`02`で説明した判断の理由。

ただし、これが一般論としてのLLM生成の財務回答(例えば大企業のFAQボットが決算数字を自然文で答える場合)だったら話は別: その場合も同じ発想が使える。**「答えの数字が、実際に参照した決算資料(retrieved_context)に書かれている数字と一致しているか」**を照合すればいい。「本当の正解額を知っているか」ではなく、「引用元の資料の数字と一致しているか」という照合問題に落とし込める点は、LinkedInの例と全く同じ構造。

## まとめ: 「正解を知っているか」ではなく「根拠と一致しているか」

| | 正解ベースの検証 | 根拠ベースの検証(groundedness、今回採用) |
|---|---|---|
| 必要なもの | 客観的な正解(criticが知っている必要がある) | 回答生成時に使った検索結果(retrieved_context) |
| 誰も正解を知らない質問 | 検証不能 | 検証可能(検索結果と照合するだけ) |
| criticがやること | 採点 | 照合 |

これがRAG(検索拡張生成)の評価で実際に使われている考え方で、"faithfulness"や"groundedness"と呼ばれる。「LLMの回答が本当に正しいか」ではなく「LLMの回答が、渡された資料の範囲を超えて話していないか」を機械的にチェックする、という設計。これが`handle_semantic`の返り値を`(answer, search_results)`のtupleに変更し、`retrieved_context`をStateに追加した理由。
