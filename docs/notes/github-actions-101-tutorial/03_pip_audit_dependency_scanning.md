# GitHub Actions 101: pip-auditで何を、なぜ守るのか

> `01`・`02`の続き。lint(ruff)・test(pytest)に続く3つ目のチェック。
> エージェント化やMCP化はしない(理由は下記)、`ci.yml`にコマンドを1行足すだけ。

---

## pip-auditは何をする道具か

**Input**: `requirements.txt`(このリポジトリの場合、300以上のパッケージが並んでいる)
**Output**: その中に、既知の脆弱性(CVE)が報告されているバージョンのパッケージが無いかの一覧
**なぜ**: 自分で書いたコードにバグが無くても、**使っているライブラリ自体に脆弱性がある**ということは普通に起こる。それを検出するのがこのツール

やっていることは単純: `requirements.txt`にある「パッケージ名+バージョン」の組み合わせを、PyPIの脆弱性データベース(PyPI Advisory Database / OSV)と1つずつ照合するだけ。自分のコードは一切読まない(lintやpytestとは対象が違う)。

## 今、これが無いとどう危ないのか

このリポジトリの`requirements.txt`には300個以上のパッケージが入っている(`pip freeze`の全量)。この中の**どれか1つでも**、今のバージョンに脆弱性が報告されている可能性がある。具体例(実際に過去よくあったパターン):

- `PyYAML`の特定バージョン: 信頼できない入力を`yaml.load()`すると任意コード実行が可能だった脆弱性
- `cryptography`や`requests`の特定バージョン: 暗号処理や証明書検証の不備
- 依存の依存(自分が直接importしていないライブラリ)にまで脆弱性が潜んでいることもある

**今の状態(pip-audit無し)だと、これに気づく方法が無い。** 自分でコードを書いてテストが全部通っても、「使っているライブラリの中に脆弱性がある」ことには一切気づけない。気づくとしたら、実際に何か悪用されてから、というのが一番怖いパターン。

## 追加すると何が変わるか

push/PRのたびに、`requirements.txt`の中身を自動でスキャンし、既知の脆弱性が見つかったパッケージがあれば**その場で一覧表示**してCIが❌になる。これにより:

- 「使っているライブラリに脆弱性があるかどうか」を**毎回確認する作業自体が要らなくなる**(自動化の本質、`01`で話した通り)
- 脆弱性が新しく公表された場合も、次にCIが走ったタイミングで検出できる(該当データベースは日々更新される)
- どのパッケージのどのバージョンが危険かが一覧で分かるので、対応(アップグレード)すべき箇所がすぐ分かる

## このチームの実務との対応

このSAPのチーム(Security Patch Quality Assurance)がやっているのは、まさに「報告された脆弱性に対するパッチの品質を確認する」こと。pip-auditは規模もやることも全然違うが、**「既知の脆弱性を継続的にチェックして、見逃さない仕組みを作る」という発想自体は完全に同じ**。自分のプロジェクトの依存関係という小さいスケールで、同じ考え方を実践した、という説明ができる。

## 実装(ci.ymlへの追加)

```yaml
- run: pip install pip-audit
- run: pip-audit -r requirements.txt
```

たったこれだけ。lint/testの時と同じく、既にあるstepsの後ろに2行足すだけで完結する。
