## 1. GitHub Actionsが無かったら何をすることになるか

GitHub Actionsは「新しい能力」を追加する道具ではない。**自分が手でやっていた作業を、GitHubのイベント(push/PRなど)をきっかけに自動でやらせる道具**。

なので、まず「無かったらどうするか」から考えると分かりやすい。

**GitHub Actionsが無い世界(今の`langchain-rag-explorer`)**:
```bash
# コードを直して、コミットする前に...
$ pytest src/embed_test.py   # 自分の手でテストを実行
# 通ったのを確認してからpush
$ git push
```
これは今すでにできている。何も困っていない、はず。ただし:
- テストを実行し忘れてpushしても、GitHub上は何も教えてくれない
- 将来PRベースの開発(他の人のレビューを通す、複数ブランチが並行する)になったとき、「このPR、テスト通ってるか?」を毎回自分の目でコードを読んで判断することになる
- チェックすべき項目が増えてくる(lint、依存の脆弱性チェックなど)ほど、手で全部回すのを忘れがちになる

**GitHub Actionsがある世界**:
```bash
$ git push
# → GitHub側が自動で「pytestを実行」「lintを実行」を代行してくれる
# → 結果はPR画面に✅/❌として出る。自分の手元では何もしなくていい
```

**結論**: 「無いとできないこと」は無い。「無いと、自分が覚えていないと毎回忘れる/サボれる作業を、忘れようがない形で強制してくれる」のがGitHub Actions。ユーザーが持っていた「プロダクションに載せる要件をテストとして用意しておいて、それを自動化する」というイメージは、**CI(継続的インテグレーション)という用途に限れば正しい**。ただしActionsができることはCIだけではなく、「GitHubで何かが起きたら何かをする」という汎用の自動化基盤全般(定期実行、リリース時の処理なども含む)。このプロジェクトで使うのはそのうちの「pushやPRをきっかけに品質チェックを自動で回す」というCI用途の部分だけ。

## 2. 出てくる語彙

### Workflow(ワークフロー)

**Input**: なし(定義そのもの)
**Output**: `.github/workflows/`配下の1つの`.yml`ファイル
**なぜ**: 「どんな時に(trigger)」「何を(jobs)」やるかをまとめて書く、1つの自動化のまとまり。1リポジトリに複数個置ける(ci.yml, deploy.ymlなど)

```yaml
name: CI
on:
  push:            # pushされたら
  pull_request:     # PRが作られた/更新されたら
```

### Job(ジョブ)

**Input**: なし
**Output**: 1つの独立した実行単位。それぞれ別のマシン(runner)で並列に走る
**なぜ**: 「lintのジョブ」「testのジョブ」のように分けると、片方が失敗してももう片方の結果は独立して見える

```yaml
jobs:
  test:
    runs-on: ubuntu-latest   # GitHubが用意する使い捨てのLinux仮想マシン(runner)上で動く
    steps:
      - ...
```

### Step(ステップ)

**Input**: 前のstepまでの状態(同じjob内ではファイルシステムを共有)
**Output**: 1つのコマンド実行、または既製の部品(action)の実行
**なぜ**: jobの中身を「コードを取ってくる」「Pythonを入れる」「依存を入れる」「pytestを実行する」のように1つずつの手順に分解する

```yaml
    steps:
      - uses: actions/checkout@v4        # リポジトリのコードをrunnerに持ってくる
      - uses: actions/setup-python@v5    # Python環境を用意する
        with:
          python-version: "3.11"
      - run: pip install -r requirements.txt
      - run: pytest src/embed_test.py    # ← 自分が手元でやっていたコマンドそのもの
```

**ここが一番大事なポイント**: `run:`の中身は、普段ターミナルで打っているコマンドと同じもの。GitHub Actionsを学ぶというのは、新しいコマンドを覚えることではなく、「手元で打っていたコマンドを、いつ誰が実行するか」をYAMLで宣言する作業。

## 3. Lint と Test の違い(ここが分かっていなかった部分)

どちらも「コードの品質を機械的にチェックする」点は同じだが、チェックの仕方が根本的に違う。

| | Test(`pytest`) | Lint(`ruff`) |
|---|---|---|
| コードを**実行するか** | する(動的) | しない(静的、読むだけ) |
| 何をチェックするか | 「この入力を渡したら、期待した出力が返るか」という**振る舞い** | 「未使用のimportがある」「使われていない変数がある」「危険な書き方(比較演算子の誤用など)をしている」という**書き方そのもの** |
| 見つかるもの | ロジックのバグ | 将来バグの温床になりそうなコード、読みにくいコード、単純な書き間違い |
| このリポジトリでの例 | `src/embed_test.py`が「埋め込み関数が正しいベクトルを返すか」を確認している | `ruff check src/`をかけると、例えば`graph_router.py`で使っていない`import`が残っていないか、といったことを**実行せずに**指摘してくれる |

具体例: `def foo(x): y = 1; return x`のような、宣言したのに使っていない変数`y`があるコードは、**実行すれば普通に動いてしまう**(エラーにならない)。testでは引っかからない。しかしlintは「使われていない変数がある」という**書き方の問題**として静的に検出する。「動くけど汚い/将来事故りやすい」コードを拾うのがlintの役割。

## 4. Dependency audit(`pip-audit`)は何が違うのか

前回のプランファイルに書いた`pip-audit`は、lintでもtestでもない3つ目のチェック。

- Lint: **自分が書いたコード**の書き方をチェック
- Test: **自分が書いたコード**の振る舞いをチェック
- Dependency audit: **自分が書いていない、`requirements.txt`に書いてある外部ライブラリ**に、既知の脆弱性(CVE)が報告されていないかをチェック

自分のコードが完璧でも、使っている`langchain`や`langgraph`のあるバージョンに脆弱性が見つかっている、ということはあり得る。それを検出するのが`pip-audit`。Security Patch QAチームの実務(「報告された脆弱性のパッチ品質を確認する」)に一番近い発想のチェックなので、この求人向けには特に説明しやすい項目。

## 5. 自分のプロジェクト(`langchain-rag-explorer`)に当てはめると

今このリポジトリには`.github/workflows/`が存在しない = 上に書いた3つのチェックは、すべて「自分がpush前に手元でやるかどうか」に懸かっている(実際には`ruff`もまだ導入していないし、pushのたびに`pytest`を毎回手で回してもいない)。

`02`で作る`ci.yml`がやることは、要するに:

```
push または PR が発生したら:
  1. ruff check src/          ← 書き方チェック(新規追加)
  2. pytest src/embed_test.py ← 振る舞いチェック(今も手ではできる、自動化されていないだけ)
  3. pip-audit                ← 依存の脆弱性チェック(新規追加、Security QAチーム向けの一手)
```

これだけ。新しい概念というより、「今バラバラに(あるいはまだ)自分の頭の中でやっている3つのチェックを、YAMLに書き出して、GitHubに代行させる」という話。
