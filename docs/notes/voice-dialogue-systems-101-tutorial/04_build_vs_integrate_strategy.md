# どう作るか: ゼロから構築 / 既存モデル改造 / 既存APIの統合

> 2026-10-01、02を見た後の疑問から。「音声を自力で1回失敗した経験があるので、
> いきなりフルデュプレックスの研究レベルのモデリングに踏み込んで大丈夫か」という懸念と、
> 「Geminiのような既存のマルチモーダルAPIを音声ラッパーとして使えないか」というアイデアの2つを整理する。

---

## 1. アイデア: Gemini Live APIを音声ラッパーとして使う(確認済み、実在する)

Web検索で確認した結果、**これは今まさに本番レベルで使える機能として存在する**。

- Google の **Gemini Live API**(Multimodal Live API)は、WebSocket経由で音声を双方向にストリーミングする、**ASR→LLM→TTSという別々の段階を挟まない、ネイティブな音声→音声**のAPI。
- 現行モデルは Gemini 2.5 Flash Native Audio(Vertex AIで本番運用レベル、SLA付き)、さらに Gemini 3.1 Flash Live がプレビューとして登場済み。
- **バージイン(割り込み)にネイティブ対応**、関数呼び出し(ツール統合)、Google検索によるgrounding、70言語対応。
- 音声そのもの(トーンや間、抑揚)を直接知覚し、テキスト全体の生成を待たずに喋り始められる、と説明されている — つまり[01_pipeline_vs_end_to_end.md](01_pipeline_vs_end_to_end.md)で言う「フルデュプレックス型」の挙動を、**自分でモデルを学習させなくても、API呼び出しだけで手に入れられる**。

**結論**: このアイデアは実行可能。「Moshiを自分で一から再現する」のではなく、「Geminiの音声ネイティブAPIを土台にして、その上にアプリケーション/評価の層を作る」という進め方が、技術的に成立する。

### 具体的な最小デモ案: 今あるRAGアプリをGemini Liveで音声化する

「必須かと言われたら多分いらないが、やっておくといい」という位置づけの軽いPoC案。

- 今の`langchain-rag-explorer`(LinkedIn人脈データ・支出データに対するRAG+集計)に、Gemini Live APIを使って音声入出力の層を1枚足す。
- 例: 「LinkedInでどれくらい留学生と繋がった?」と**音声で**質問し、**音声で**答えが返ってくる。
- 目的は「ラッパー方式が技術的に動くことを自分の手で確認する」こと。[01](01_pipeline_vs_end_to_end.md)で言う「パイプライン型寄り」のデモだが、既存資産の再利用なので工数が小さく、Gemini Live自体の挙動(バージイン・遅延)を体感するための足がかりになる。
- **優先度は低い** — 本命のプロジェクト選定とは別に、時間が余った時にやる位置づけ。

## 2. 本質的な懸念: フルデュプレックスを個人でゼロから作るべきか

本人の指摘(要約):

> 音声は過去に1回挫折している(フーリエ変換のところ)。いきなりフルデュプレックスのモデリングに行くより、まず「API会社がどうプロセスを処理しているか」を基礎から勉強すべきでは。個人レベルでわざわざ一から開発する意味があるのか疑問。研究(Kyutai, Googleのような企業)が既にやってくれているなら、それを統合して、ちゃんとユーザーの意図を汲み取れているかを見る方に回った方が、評価やアプリ作りという自分の得意な場所で動けるのではないか。

これは妥当な指摘。理由を技術面から補強すると:

- フルデュプレックスの音声トークン化モデル(Mimiのようなニューラルコーデック)や、音声言語モデル自体の事前学習には、大規模な音声データと計算資源が必要で、個人の学部生プロジェクトの範囲を明確に超える。これはKyutai(Moshi)やGoogle(Gemini Live)のような組織が研究開発している領域であり、個人が「車輪の再発明」をする価値は薄い。
- 一方、**RAGプロジェクトで既にやってきたこと**(既存の埋め込みモデル・LLMを土台にして、その上に検索ロジック・critic node・評価パイプラインを組む)と、**同じ構造**がここでも通用する。「基盤モデルは自分で作らない、使う」というのは今までの進め方と一貫している。
