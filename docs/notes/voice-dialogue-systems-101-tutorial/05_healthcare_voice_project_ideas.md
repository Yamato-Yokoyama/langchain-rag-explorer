## 自分がこの領域に行けるのか(正直な評価)

- voize・Doctena・MantraAssistのような会社が採用したいのは、**臨床の専門家ではなく、音声AIプラットフォームを作るソフトウェア/MLエンジニア**。医療知識は入社後にドメインとして学ぶもので、応募時点の必須要件ではないことが多い。
- 一方、MR(医薬情報担当者)や薬剤系の話は、規制・専門知識の壁が厚く、エンジニアとして入る道筋とは別物 — **これは避けるという判断で合っている**。
- 現実的な入り口は「ヘルスケア業界特化の会社」の**Voice AI/Applied AIエンジニア(Werkstudent)**として応募すること。業界知識ゼロからでも、技術力(音声API統合・評価設計)を見せられれば土俵には立てる。

## 案1(最初の一歩として推奨): 多言語の予約受付ボット

**選んだ理由**: 自分自身が留学生として体験した実際のペインポイント(ドイツ語でしか予約できないクリニックが多い)に直結しており、医療ドメイン知識がほぼ要らない。今の`router.py`の集計・意図分類ロジックと構造が近く、着手しやすい。

### 内容

- 架空の(または公開されている)クリニックの予約枠データを用意し、Gemini Live APIで**音声での多言語(独・英)予約受付**を作る。
- 「ドイツ語しかできないスタッフしかいない」状況を想定し、英語話者が音声だけで予約を完了できるかを検証する。
- 関数呼び出し(function calling)で、空き枠の検索・予約確定・確認メッセージ生成を行う(= Gemini Liveのツール統合機能をそのまま使う)。

### 評価軸(02のカテゴリと接続)

- **分類(カテゴリ1)**: 発話の意図(予約・変更・キャンセル・問い合わせ)を正しく分類できているか
- **信頼度推定/キャリブレーション(カテゴリ3)**: 「聞き取れた内容にどれくらい自信があるか」が低い時に、ちゃんと聞き返しているか。数字で測れる指標(例: 誤った予約確定の発生率)を作れる
- **業務インパクト**: Doctena等が報告している「予約数の増加率」のような、ビジネス指標に接続した言い方ができる

## 案2: 臨床記録アシスタント(voize/Dragon Copilotの再現実験)

**2026-10-01追記: 当初「案1の後に」としていたが、以下2点により評価を修正した。案1と並ぶ有力候補として扱う。**

### 修正理由1: 既存スキルとの距離が思ったより近い

`src/receipt_mcp_server.py`で既にやっていること(レシート画像という非構造データ→厳密なJSONスキーマへのLLM抽出)と、「診察会話という非構造データ→SOAP形式へのLLM抽出」は**構造的にほぼ同じ**。スキーマを差し替えるだけで技術的骨格は使い回せる(本人の指摘で気づいた点)。

### 修正理由2: 評価用の公開データセットが実在する(確認済み)

「医療知識がないと生成物の正誤を判定できない」という当初の懸念は、以下の公開ベンチマークで解消できる。

- **ACI-Bench**: 207件の完全な医師-患者会話とSOAPノートのペア([arXiv:2306.02022](https://arxiv.org/pdf/2306.02022))
- **MTS-Dialog**: 1,701件の会話-ノートペア、6診療科をカバー
- 両方とも**MEDIQA-Chat 2023 shared task**(ACL系ワークショップの共有タスク)で実際に使われた実績がある([ACL Anthology](https://aclanthology.org/2023.clinicalnlp-1.52.pdf))

→ 公開された正解ノートとの一致度(ROUGE等の標準的なNLG評価指標)で機械的に評価できる。自分の医学知識で正誤判断する必要がない。**RETECOやMTEBと同じ「外部検証可能なベンチマークがある」という条件を満たす** — これは案1(予約ボット)にはまだない強みでもある。

### 内容

- ACI-Bench/MTS-Dialogの会話トランスクリプトを入力し、構造化された診療メモ(SOAP形式: Subjective/Objective/Assessment/Plan)を自動生成する。
- 生成されたメモを、データセット付属の正解ノートと比較して評価する(RAGのcritic nodeと同じ発想 — 生成物が元の会話内容に忠実かをチェックする延長)。
- 音声での利用を想定するなら、テキストの会話データをTTSで音声化してからGemini Live/ASRに通す、という経路も作れる(医療音声データそのものを扱う必要がないため、プライバシー上も扱いやすい)。

## 推奨ステップ順(2026-10-01修正版)

案1・案2はどちらも現実的。優劣ではなく性質が違う:

- 案1(予約ボット): ドメイン知識の壁が最も低い。自分自身の実体験(独語オンリーの予約)に直結。ただし外部ベンチマークがまだない。
- 案2(臨床記録): 外部検証可能なベンチマーク(ACI-Bench/MTS-Dialog)がある。`receipt_mcp_server.py`との技術的な近さもある。ただし医療文脈を正しく読み解くための多少の学習コストはかかる。

どちらを先に着手するかは、「自分の実体験に近い方から」か「外部ベンチマークがある方から」かという優先順位の好み次第 — 技術的な難易度ではもう差がないと考えてよい。

### AWS vs Azureの実態(本人の「Azureは使いづらいのでは」という疑問への回答)

半分正しく半分言い過ぎ、というのが調査結果。

- Azureの弱点(確認済み): BAA対応サービス数がAWSより少ない(約80 vs 150)、料金体系が複雑、インデックス検索性能がAWS HealthLakeに15〜20%劣るという報告
- Azureの強み(確認済み): FHIRサーバー・分析基盤・AI層が統合されており、Epic(大手電子カルテ)との統合が単体プロジェクト不要で済む — ここはAWSより優れている

単純に「AWSの方が良い」とは言い切れない。
