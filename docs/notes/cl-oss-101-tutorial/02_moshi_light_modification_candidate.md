# 候補メモ: Moshi(音声対話OSS)を軽く改造する

> 音声対話システム(軸2)の検討中に出てきた案。[voice-dialogue-systems-101-tutorial/04](../voice-dialogue-systems-101-tutorial/04_build_vs_integrate_strategy.md)で
> 「本線はエンジニアアプローチ(既存の本番APIを統合)で進む」と決めたため、
> ここでは**軸2の本線としてではなく、軸3(CL×OSS、たまに拾う枠)の候補**として記録する。

## 案の内容

Kyutaiの**Moshi**(オープンソースのフルデュプレックス音声対話モデル)を実際に動かし、軽くファインチューン/評価を拡張してみる。

- [01_pipeline_vs_end_to_end.md](../voice-dialogue-systems-101-tutorial/01_pipeline_vs_end_to_end.md)で解説した「音声トークンのストリーム処理」の仕組みを、コードレベルで実際に触って理解する。
- 本番運用を目指すものではなく、**「中身を読んだ・動かした」という経験値**を積むための実験枠。
- Haystack #12867(CJKトークナイズ)と同じ位置づけ — 常時進行中にはしない、見つけたら/気が向いたら拾う。

## なぜ軸2の本線にしないか

- 本線(軸2)は[04](../voice-dialogue-systems-101-tutorial/04_build_vs_integrate_strategy.md)の通り、就職活動の時間軸(JASSOの返済・2028年卒業)を考えると「エンジニアとして早く形にする」ことを優先し、Gemini Live等の本番APIを統合する方向で進める。
- Moshiの内部を触る体験は価値があるが、研究レベルのモデル改造に時間をかけすぎると本線が遅れるリスクがある → 息抜き枠に切り出すことで、本線の進捗を妨げないようにする。
