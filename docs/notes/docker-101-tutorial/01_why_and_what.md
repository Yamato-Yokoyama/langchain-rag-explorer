## 元々あった誤解1: 「Dockerにお願いすればデプロイされる」ではない

Dockerは**アプリを箱詰めする技術**であって、**ホスティング先ではない**。
Dockerだけでは「公開される」ことにはならない。箱詰めした後、**どこで動かすか**
(自分のPC、Hugging Face Spaces、Cloud Runなど)は別に決める必要がある。

- Docker = 箱詰めする道具
- 公開デプロイ = 箱詰めしたものを、誰かのサーバーに置いて動かす行為(別の話)

今回は前者(箱詰め)だけをやる。後者(公開)はIssue #41の判断通り見送り。

## 元々あった誤解2: GitHub Pagesでは動かせない

GitHub Pagesは**静的サイト専用**(HTML/CSS/JSだけ配信する)。Pythonのような
サーバーサイドのプログラムを実行する機能が無いので、Chainlit(常時起動する
Pythonサーバー)は構造的に載せられない。これは設定でどうにかなる話ではなく、
GitHub Pagesという仕組み自体の制約。

## Dockerが実際に解決する問題

このプロジェクトを新しいPCで動かすには、今こうする必要がある:

1. Python 3.11を用意する(バージョンが違うと動かないこともある)
2. venvを作る
3. `pip install -r requirements.txt`(300以上のパッケージ、OS差で失敗することもある)
4. `.env`にAPIキーを書く
5. 初回実行時にBGE-M3モデルがダウンロードされる

これを毎回、新しい環境でやり直すのが「私の環境では動くのに」問題の主な原因。
Dockerは、この手順(1〜3)を**レシピとして1つのファイルに固定**し、
どの環境でも同じ結果が再現されるようにする。

## 3つの用語: Dockerfile / イメージ / コンテナ

| 用語 | 何か | たとえ |
|---|---|---|
| **Dockerfile** | 手順書(「Python 3.11を使う」「コードをコピー」「pip installする」「起動コマンド」を書いたテキストファイル) | レシピ |
| **イメージ(image)** | Dockerfile通りに組み立てた「完成品」、まだ動いていない静的な状態 | 冷凍食品 |
| **コンテナ(container)** | イメージを実際に起動して、動いている状態 | レンジで温めて食べている状態 |

1個のイメージから、コンテナは何個でも起動できる(同じ冷凍食品を何個温めてもいい、という関係)。

## このプロジェクトに当てはめると: シンプルな構成で済む

`src/rag_pipeline.py`で`chromadb.PersistentClient(path=...)`を使っている
(`rag_pipeline.py:104`)。これは**ChromaDBを別サーバーとしてではなく、
Pythonプロセスに埋め込みで使っている**ということ。つまり:

- ChromaDB用に別コンテナを立てる必要は無い
- **アプリ用のコンテナ1個だけ**で完結する
- 複数コンテナを繋ぐ`docker-compose`は今回は不要(将来DBを外部化する場合は別)

## ゴール(`02`で作るもの)

`docker build`でイメージを作り、`docker run`(または`docker compose up`)一発で
Chainlitアプリが起動する状態にする。READMEに「`docker compose up`で動かせます」
の1行が書ける状態がゴール。公開デプロイ(Hugging Face Spaces等)は、Issue #41の
判断通り今回は行わない。
