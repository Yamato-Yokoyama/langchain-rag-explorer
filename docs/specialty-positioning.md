# 専門性の言語化: 「システムの失敗を言語理論で診断できるエンジニア」

> [docs/why.md](why.md)から分割(2026-08-27)。「なぜこのプロジェクトをやるか」の中でも専門性の言語化に絞った内容。

何年も「言語が好き」「CS も言語学も唯一続いている」という漠然とした自己認識のまま、専門性を一言で言えずにいた。2026-08-27、このプロジェクトのデバッグセッション中に出た言語化がしっくり来たので、ここに固定する。

**弱いバージョン(これまでの自己認識)**: 「言語が好きで、CSも学んでいて、DeepLに興味がある」— 好みの表明であって、技能の主張になっていない。

**このプロジェクトが実際に示した技能**: Speech Act theory、Common Ground(Stalnaker)、QUD理論(Roberts)、Griceの公理といった語用論の理論を使って、RAGシステムの失敗を**型ごとに分類し**、型ごとに**別の対処法**を選ぶ、という診断行為を繰り返した(具体例: [insights.md](../daily/interview-prep/insights.md) Insight 01-05、[pragmatics-in-rag-query-processing.md](../daily/interview-prep/pragmatics-in-rag-query-processing.md))。

「言語が好きなAIエンジニア」ではなく、**「NLPシステムの失敗を言語理論で診断できるエンジニア」**。これは狭いが再現性のある技能で、DeepLやSAPのような会社で言えば「なぜこのRAGはこのクエリで間違えるのか」を理論的な語彙で説明し、対処法を型ごとに選び分けられる、という実務上の価値に直結する。

**このプロジェクトを続ける理由がここで1本につながる**: 「言語学を前セメスターで学んだから」という偶然の理由づけではなく、**このプロジェクトを完成させ続けること自体が、この専門性を実証する主たる手段**になっている。就活の成果物としても、専門性の言語化としても、同じ1本の作業が両方を進める。だから「別のアプリ」や「別の教材」に手を広げるのではなく、このプロジェクトを深掘りし続ける、という判断には根拠がある。

**迷った時の使い方**: 次にやることを決める時、「これはRAG/NLPシステムの失敗診断という専門性を伸ばすか?」を判定基準にする。イエスならこのプロジェクトの延長で進める。ノーなら、それは別トラックの学習([snlp2-exam-prep.md](snlp2-exam-prep.md))として意識的に切り分ける。
